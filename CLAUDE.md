# Working in this repo

Reference for a future Claude Code session (or any agent) picking this
project up. Practical notes, not narrative — the "why" behind each is in
docs/ARCHITECTURE.md and docs/SETUP.md, which are kept in sync with this.

## Shape of the thing

`make build` / `make flash` / `make clean`, driven by an ordinary
Makefile that calls CodeWarrior's command-line compiler, assembler,
linker and flash programmer directly. **No Eclipse project files, no
`ecd.exe`, no IDE.** Edit in VS Code (`Ctrl+Shift+B` → `make build`) or
anything else.

```
Makefile              the build: flags + rules
src/                  application sources
linker/               .cmd linker command files, device .mem/.tcl
flash/flash.cfg       device/interface config for fflash
config/toolchain.mk   generated by tools/Detect-Toolchain.ps1, gitignored
tools/                Detect-Toolchain.ps1 — the one-time "configure" step
```

PowerShell appears exactly once, in `tools/Detect-Toolchain.ps1`
(the `./configure` equivalent). Everything else is `make` + POSIX shell.
Don't reintroduce PowerShell into the build path.

## The one fact that matters most

**Toolchain is CodeWarrior for DSC v11.2 + SP1** at
`C:\Freescale\CW MCU v11.2`. Not v11.1 — that's a different product
("CodeWarrior for MCUs", `CW-MCU10`) and it *cannot* build current
MCUXpresso SDK releases for this board, no matter how patched. If you
hit `Linker command file error ... Expecting: MEMORY`, or
`Undefined : "Fmemset"` / `"ARTDIVU32UZ_2"`, check `CW_ROOT` in
`config/toolchain.mk` before anything else.

Install files (NXP product page `CW-DSC`, needs a free NXP account you
cannot log into on the user's behalf): `CW_MCU_v11.2_b221206.exe` (GUI
wizard, select the **DSC** component), `com.freescale.mcu11_2.dsc.
updatesite.zip`, and `com.freescale.mcu11_2.DSC_devices.win.sp.v1.0.26.
zip` (device support — MC56F83xxx lives here).

Applying the two zips through CodeWarrior's own Eclipse "Install New
Software" can fail — its bundled 2007-era JVM has a real
`IllegalStateException` bug. Don't fight it: each zip's
`binary/*_root_*` entry is itself a zip rooted at `MCU/`; extract that
straight over the install directory
(`unzip -o -q <root_file> -d "C:\Freescale\CW MCU v11.2"`).

## Gotchas that cost real time — don't rediscover these

1. **`fflash` fails *silently* without `-gdi=`.** Given no explicit GDI
   driver it picks one that can't reach this board's OSJTAG probe, then
   exits non-zero printing **nothing** — no stderr, no `-l<file>`
   content, nothing in the Event Log. Not a crash, not a permissions or
   session-isolation problem (all ruled out; identical interactively,
   elevated, and headless). The Makefile always passes
   `-gdi=$(GDI)`, derived from `fflash.exe`'s own directory — a
   CodeWarrior install has more than one copy of `dsc_pne_gdi.dll`, and
   the one beside `fflash.exe` is the right one.

2. **`fflash` leaves the target halted.** After `make flash` the board
   does nothing until its reset button is pressed. There's no
   reset-and-run flag. If firmware "doesn't work" after flashing, ask
   for a reset before debugging anything else.

3. **First board + toolchain-version pairing needs a one-time JM60
   firmware update**, and only CodeWarrior's **IDE** can do it
   (`eclipse\cwide.exe` → Debug-launch → it prompts to bridge jumper
   **J6**). Symptom without it: `"unknown connection error"`. This is
   the only situation where the IDE is required.

4. **Only one client can hold the debug interface.** A stale `cwide.exe`
   or `ccs.exe` process will block `make flash`. Check `tasklist` and
   have the user close the IDE.

5. **`flash/flash.cfg`** came from `{CW}\MCU\M56800x Support\56800E
   flash programmer\MC56F837xx.cfg` — it targets `mcu mc56f83789`
   despite the "837xx" name. Confirmed working on hardware.

6. **GNU Make needs a POSIX `SHELL`.** `config/toolchain.mk` sets it to
   Git for Windows' bash; without it Make uses `cmd.exe` and every
   recipe using `mkdir -p`/`rm -rf` breaks. Also: Windows PowerShell
   5.1's `-Encoding utf8` writes a **BOM**, which makes Make report
   `missing separator` on line 1 — `Detect-Toolchain.ps1` deliberately
   writes `toolchain.mk` BOM-less via `UTF8Encoding($false)`.

## Verifying hardware yourself

Don't ask the user to watch a serial terminal — read it directly.

```powershell
$port = New-Object System.IO.Ports.SerialPort COM4,115200,None,8,One
$port.ReadTimeout = 2000
$port.Open(); Start-Sleep -Milliseconds 300
$port.ReadExisting() | Out-Null      # drain
$port.Write("ping")                   # only echoes if firmware echoes
Start-Sleep -Milliseconds 800
$port.ReadExisting(); $port.Close()
```

The COM number varies — find it via
`Get-CimInstance Win32_PnPEntity | Where-Object { $_.DeviceID -match 'VID_15A2' }`;
the "OSBDM/OSJTAG - CDC Serial Port" entry names it. VID `15A2` is
Freescale/NXP's.

Note the boot banner prints **once at reset**, so opening the port
afterwards captures nothing. Either open the port first and have the
user reset, or (better) probe liveness in a way that doesn't depend on
timing.

The stock `src/hello_world.c` blinks a **~2 Hz green heartbeat LED**
(`LED_GREEN_TOGGLE()` + `SDK_DelayAtLeastMs`), which is the
UART-independent liveness signal. It does *not* echo serial input — the
stock demo's `GETCHAR()` echo loop was removed because it blocks and
would stall the heartbeat.

If the user reports LEDs behaving differently than before: the OSJTAG
debug-activity LEDs light while CodeWarrior's debugger is attached.
Their absence under `make flash` is expected, not a fault.

## Board physical notes

- **J8** — the OSJTAG debug + USB-UART port. Verify by the PCB
  silkscreen, never by physical position; the board has several USB
  connectors and "the middle one" is not reliable.
- **J6** — 2-pin jumper, bridged only during a JM60 firmware update.
- Don't assume a connected USB device is this board. It enumerates under
  VID `15A2`. Other NXP boards (FRDM/MCU-LINK, VID `1FC9`) are easy to
  plug in by mistake — check `Get-CimInstance Win32_PnPEntity` first.

## Scope limits, deliberately

- **Only `flash_ldm_lpm_debug`** is implemented. Its flags were
  transcribed from a real build's `.args` files, not guessed. The
  Makefile hard-errors on other `CONFIG` values rather than inventing
  flags — keep that standard; confirm flags from a real build before
  adding `sdm`/`release`.
- **No scripted debugging.** `cwidec.exe` takes no script flag (`-help`
  isn't recognized; it drops into an interactive TCL REPL on stdin), and
  there's no GDB target for this core. A previous revision's
  `Debug.ps1` + `debug/*.tcl` were guesswork that never ran, and were
  removed. Don't recreate them speculatively.
- SDK sources are **referenced by path**, never vendored — `SDK_ROOT` in
  `config/toolchain.mk`.
